# Build a finished experience, not just functional endpoints

Load during planning and both reviews. Preserve project scope. The machine-checkable `experience_profile: v08` is a compatibility schema identifier; use it for **all new builds**, keeping historic plans readable. See `examples/rigorous-build-plan-v08.json`.

**Plan as a person using the product.** Before implementation write: (1) what they see or hear before data exists, (2) the first meaningful action, (3) one credible mistake or interruption, (4) how they recover or continue later. Pick 2–4 distinct scenarios, always `first-run` plus another meaningful scenario. Bind each scenario to a separately labelled executable assertion-bearing test, not `print('ok')`; record expected external behavior. They complement (not replace) bound journey, edge and smoke tests. For web/desktop with actual browser tools, prioritize `keyboard-flow` and `narrow-layout`; if no browser is available, state that those were not visually verified and never fabricate screenshots.

**Implement in short loops.** For each slice: public behavior and data boundary → one failing regression assertion where practical → implementation → executable probe → manual/public-path check. Reproduce errors before fixing. Do not solve test failures by deleting tests, changing their assertions to tautologies or only testing internal helpers. Use official/current implementation documentation for unfamiliar APIs and record actual consulted sources. Include usable sample data only if it is clearly fictional and supports the first-run experience.

**Polish to feel designed, not generated.** Fit product form: CLI help should show useful commands and actionable errors; web should have a visual hierarchy, purposeful spacing, responsive states, accessible focus/keyboard paths; API/library should offer copyable examples and precise failure messages. Use domain-specific microcopy, coherent terminology and a lightweight visual language. Replace lorem ipsum, empty ornamental cards, gratuitous gradients/animations, fake testimonials, unearned marketing claims and generic 'AI-powered' prose with meaningful content. Test long labels, no data, errors and reruns. Keep typography/spacing and interaction consistent. No feature creep, broad redesign, invented user research or new dependencies merely for polish.

**Reviewer contract.** Quality challenges observable behavior and weak assertions. New-project enhanced plans also set `usability_profile: novice-v1`: while Quality is active, a simulated first-time user tries the public journey without source/test answers; a separate advocate listens and makes minimal evidence-backed repairs. Follow `references/novice-usability.md`, preserving functional contracts and safeguards. Quality approves the repaired current source, then Polish reads BRIEF.md, USABILITY.md, the app and Quality findings. Record changes and limitations. Rerun journey, edge, smoke and experience scenarios after the reviews on unchanged source. Passing commands and agent simulations do not establish human usability or accessibility.
