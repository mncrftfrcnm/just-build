# External behavior checks (CLI or loopback API)

Use for **new enhanced CLI builds** (especially Auto). This is a small user-facing contract outside the generated project's tests. It is not an independent human review, a sandbox, or a guarantee of software quality. Web/desktop surfaces retain their existing real-browser acceptance checks. Older plans without `contract_profile` remain readable.

1. Start with `examples/contract-build-plan.json` or add `"contract_profile": "external-cli"` to an enhanced CLI plan. While `plan` is active, author a *project-specific* JSON following `examples/cli-behavior-contract.json` in the run/state folder, not in the generated project's test suite. Use real fictional input and expected exact public results, never tautological assertions.
2. Freeze it with `run_tracker.py contract --state-dir "$RUN" --file <contract.json>` **before** `plan done`. It needs 2–5 scenarios, 4+ observable steps, an error case, a file-state check and a multi-step journey. Use `{python}`, `{project}/entry.py` and `{scratch}/data.json` placeholders. Scenarios use separate temp data; steps within one scenario share it. The public entry script must live inside the project. Do not execute untrusted commands or remote snippets.
3. During `verify` and again during `final-verify`, run `run_tracker.py contract --state-dir "$RUN"`. The tracker records each execution as the reserved `external-contract` label; an ordinary test cannot forge that label. All other bound acceptance checks remain mandatory. New source changes invalidate old results.
4. If a contract fails, fix the observable project behavior or explain and revise the contract **during a new planning/run cycle**; never silently weaken it to match a defect. Include first-run, persistence, one credible mistake and recovery where relevant.

The manifest is agent-authored, frozen into the ledger and not independently evaluated for product desirability. Execution invokes trusted project code with host privileges. Scratch data and bounded process supervision do not provide network or filesystem isolation. The supervisor terminates normal descendants, enforces time/output budgets, and rejects implicit Windows batch execution. Checks cover the entire bounded capture, so forbidden output cannot hide beyond a displayed prefix. Test output is not persisted. A separate human/live-host evaluation is still needed before marketing universal autonomous building claims.

## Structured output and input preservation

For machine-readable CLI output, a step may use `"stdout_json_equals": {"enabled": true, "count": 3}`. For API responses, a request may use `body_json_equals` with the same JSON value shape. Comparison covers the whole output/response: object key order is irrelevant, array order matters, and boolean, integer and floating-point types are distinct. `null` is a valid expectation. Extra text, duplicate object keys, nonfinite numbers, invalid UTF-8 or a different value fail. JSON expectations and observed JSON are bounded to 4096 UTF-8 bytes, 20 nesting levels and 256 value/key nodes. Existing substring assertions remain available; all selected assertions must pass. API `body_contains` may be omitted when `body_json_equals` is present.

Use CLI `"file_unchanged": ["config.json"]` when a command should preserve input bytes. Files must already exist in that scenario's scratch directory **before that step**; an earlier step may create them. The runner records their SHA-256 digests before invoking the command and compares them afterward. Missing/deleted files, links, hardlinks, directories and changed bytes fail. At most five unique portable scratch-relative paths are allowed, each at most 1 MiB (5 MiB total). Case aliases and a conflicting `file_absent` assertion are rejected. This checks bytes at the command boundaries; it does not certify that no temporary write occurred. See `examples/cli-json-contract.json` for an illustrative config-inspector schema example; adapt the entry point and expectations to the actual project, then freeze it before implementation.

These fields are optional and absent fields stay absent in normalized historic contracts, preserving their frozen hashes. They strengthen observable checks, not the trustworthiness of the manifest's author or the process sandbox.

## Local HTTP API contract (opt-in)

For an enhanced API plan with `security_profile: full`, use `"contract_profile": "external-api"` and a project-specific manifest following `examples/security/local-api-contract.json`; see `examples/secure-api-build-plan.json`. Freeze it during Plan with the **same** `contract --file` command. Run `contract` without `--file` during Verify and Final Verify; an ordinary test may never substitute for the reserved label `external-contract`. A public Securer rate-control review may reference that label when this profile is enabled.

The runner starts an explicitly named local Python entry point with the sole `--port {port}` argument and sends requests to an ephemeral **127.0.0.1** port (the app must itself bind loopback), and sends only origin-relative HTTP requests to loopback. It checks successful response, a client error, at least two successful requests from one actor, 429 with Retry-After for that same actor/path, then recovery after a short wait. It never accepts a remote URL or follows redirects. The manifest is frozen and the checked source snapshot must remain unchanged. Failing observable behavior must be fixed in the app, not hidden by replacing the frozen manifest. The example `X-Client-ID` is only a test identity; deployed rate limits should derive identity from a trusted authentication/proxy boundary and use shared atomic storage across workers. Execution of project code still uses host privileges: run only trusted or sandboxed local projects, and do not present this as a penetration test, multi-worker quota certification, or permission to probe a real deployment.
